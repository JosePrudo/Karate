# Plan de Pruebas - API Buggy Cars Rating

## 1. Alcance

**Incluido** (API REST `https://k51qryqov3.execute-api.ap-southeast-2.amazonaws.com/prod`, consumida por https://buggy.justtestit.org):

| Módulo | Endpoints |
|---|---|
| Marcas | `GET /makes/{makeId}?modelsPage=n` |
| Modelos | `GET /models/{modelId}` |
| Ranking | `GET /models?page=n&orderBy=rank\|make` |
| Dashboard | `GET /dashboard` |
| Autenticación | `POST /oauth/token`, `GET /users/current` |
| Perfil | `GET /users/profile` |
| Votos | `POST /models/{modelId}/vote` (solo sin autenticación) |
| Registro | `POST /users` (validaciones negativas) |

**Excluido:** UI web, votos autenticados (cada usuario solo puede votar una vez y el voto es permanente), actualización de perfil, rendimiento y seguridad avanzada.

## 2. Estrategia y tipos de prueba

- Funcional de API: contrato (esquema), datos y códigos HTTP.
- Negativas y de borde: recursos inexistentes, paginación fuera de rango, credenciales o tokens inválidos, validaciones de registro.
- Regresión automatizada: todos los casos son repetibles y ninguno deja datos nuevos en ejecuciones posteriores (los usuarios de prueba tienen nombres fijos).
- Prueba exploratoria previa con `curl`; de ahí salieron los resultados esperados y un defecto (ver CP-20).

## 3. Herramientas y entornos

- Karate 1.5.2 + JUnit 5, Maven, Java 25.
- Entorno: producción pública de demostración (`karate.env=dev`).
- Usuario de prueba `qa_tmp_x`; se puede cambiar con `-Dbuggy.user` y `-Dbuggy.password`.
- Reportes: `target/karate-reports/karate-summary.html`.

## 4. Roles y responsabilidades

| Rol | Responsabilidad |
|---|---|
| QA (Copilot + José Padilla) | Diseño, automatización, ejecución y reporte |
| Dueño del producto | Priorización de defectos |

## 5. Criterios de entrada y salida

- **Entrada:** API disponible y usuario de prueba activo.
- **Salida:** 100 % de los casos ejecutados, ningún defecto crítico abierto sin registrar y reporte publicado.
